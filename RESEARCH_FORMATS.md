# Исследовательские данные: форматы и воспроизводимость

Команды выполняются из корня проекта, Node.js 24+, без дополнительных пакетов. Данные, роли, backups и отчёты лежат в `data/` и не попадают в Git.

## Аудит и восстановление кэша

```powershell
npm run research -- audit
npm run research -- audit faceit
npm run research -- enrich
```

Аудит сохраняется в `data/reports/<source>-research.json`: время среза, покрытие по месяцам, поля, готовность раундов, параметры скаутинга, backtest и коэффициенты модели. Для воспроизведения среза сохраняйте копию SQLite, файл ролей и версию кода. Дата `asOf` влияет на окно формы.

`enrich` работает только с локальным BO3-кэшем: добавляет отсутствующие trade kills, traded deaths, flash assists, clutches, damage и суммы экономики. Существующие значения, исходы и составы не заменяет. Перед записью использует SQLite online backup, затем читает и обновляет данные в одной транзакции. Сырые ответы не изменяются. Повторный запуск идемпотентен.

## Исторические роли

Необязательный файл `data/roles.json` — JSON-массив. Без файла все роли неизвестны. Пример **формата**, не готовая разметка:

```json
[
  {
    "playerId": "bo3:ID_ИГРОКА",
    "role": "awp",
    "from": "2026-04-01T00:00:00Z",
    "to": "2026-07-01T00:00:00Z",
    "evidence": "Ссылка или описание вручную проверенных демо за этот период"
  }
]
```

Допустимы `entry`, `support`, `awp`, `lurker`, `rifler`, `igl`. Интервалы `[from,to)` одного игрока не пересекаются; роль выбирается по моменту доступности результата. Несколько ролей одновременно не поддерживаются. Заполняйте фактические периоды и подтверждение; не переносите сегодняшнюю роль на всю карьеру. Для прогноза отдельного прошлого матча сведения о роли также должны быть доступны до его начала; текущая разметка применяется только к описательному скаутингу.

## Раундовый feature store v1

```powershell
npm run research -- import-rounds D:/path/to/rounds.json
```

Команда принимает нормализованный JSON-массив, **не `.dem`**. Автоматического скачивания и парсинга демок пока нет. Планируемый адаптер awpy должен сопоставить Steam ID с canonical player ID источника, проверить историческую пятёрку и воспроизвести счёт карты. Не склеивайте разные источники по нику.

У каждого раунда обязательны:

| Поле | Значение |
| --- | --- |
| `matchId` | Существующий ID матча, например `bo3:123` |
| `mapId`, `map` | ID и название существующей карты этого матча; например `"456"`, `"de_mirage"` |
| `round` | Порядковый номер завершённого игрового раунда, начиная с 1, включая overtime; без warmup/restarts |
| `playersA`, `playersB` | По 5 canonical player ID в порядке стабильных teamA/teamB матча, не CT/T. Все 10 уникальны |
| `sideA` | `CT` или `T` в начале раунда; сторона B противоположная |
| `winner` | ID одной из двух команд матча |
| `equipmentA`, `equipmentB` | Сумма стоимости экипировки пятёрки на freeze end; число ≥0 либо `null`. Не суммарные траты за весь матч |
| `startedAt`, `endedAt` | UTC-время freeze end и завершения раунда, внутри матча; начало раньше конца |
| `demoSha256` | 64 шестнадцатеричных символа SHA-256 исходной демки |
| `parserVersion` | Версия парсера/адаптера, например закреплённые версии awpy + нашего адаптера |
| `tickRate`, `freezeEndTick`, `endTick` | Положительный tick rate и возрастающие целочисленные ticks для раунда |

Схематический пример; замените все идентификаторы, хеш и времена реальными данными перед импортом:

```json
[
  {
    "matchId": "bo3:123",
    "mapId": "456",
    "map": "de_mirage",
    "round": 1,
    "playersA": ["bo3:101", "bo3:102", "bo3:103", "bo3:104", "bo3:105"],
    "playersB": ["bo3:201", "bo3:202", "bo3:203", "bo3:204", "bo3:205"],
    "sideA": "CT",
    "winner": "bo3:TEAM_A_ID",
    "equipmentA": 4000,
    "equipmentB": 4000,
    "startedAt": "2026-06-01T10:01:00Z",
    "endedAt": "2026-06-01T10:02:35Z",
    "demoSha256": "SHA256_ИСХОДНОГО_ФАЙЛА",
    "parserVersion": "awpy:<version>;adapter:1",
    "tickRate": 64,
    "freezeEndTick": 3840,
    "endTick": 9920
  }
]
```

Идентичность строки — `(matchId,mapId,round)`. Импорт проверяет весь файл до записи, создаёт backup и выполняет upsert атомарно. Ошибка отклоняет весь файл. Перезапись по тому же ключу позволяет исправить разбор; журнал версий отдельных раундов пока не реализован, предыдущий вариант остаётся в backup.

«Полная демка Mirage» на экране аудита означает: есть все номера раундов от 1 до итогового `scoreA+scoreB`, количество побед стороны A равно `scoreA`. Не менее 300 различных матчей с такой картой, отсутствие неполных импортированных Mirage и <5% раундов с пропуском хотя бы одного значения стартовой экономики дают готовность базового round-набора. Это проверка структуры, не верификация корректности самого демо-парсера. Kill/flash/position события, потери тиков, качество идентичностей и правильность семантики ещё проверяются отдельно перед обучением.

## API

- `GET /api/research?source=bo3` — аудит текущей базы.
- `GET /api/scouting?source=bo3&days=90&minMatches=10&asOf=2026-09-20T00:00:00Z` — срез формы до указанного момента.
- `GET /api/export?source=bo3&type=scouting&days=90&minMatches=10&asOf=2026-09-20T00:00:00Z` — CSV тех же настроек.
- `GET /api/export?source=bo3&type=players` — матчевые строки игроков, включая восстановленные поля.

Источник обязателен логически: BO3, FACEIT и PandaScore оцениваются раздельно. Неизвестные источники и неверные параметры отклоняются. CSV скаутинга экспортирует весь срез; поиск имени и фильтр роли на экране предназначены для просмотра и не меняют экспорт. Пустые метрики означают отсутствие/недостаток данных.
