# CS2 Match Lab

Локальный бесплатный MVP для исследования матчей Counter-Strike 2. Работает на **Node.js 24+**, без npm-зависимостей, платных сервисов и облачной базы. Интерфейс на русском.

**Демонстрация: https://b0gdaan.github.io/bet_ars/** — статический снимок модели, считает вероятность прямо в браузере. Сама база и импорт живут только локально.

## Запуск

В PowerShell из этой папки:

```powershell
npm start
```

Откройте **http://localhost:3210**. Либо запустите `start.cmd` двойным щелчком и откройте этот адрес. Node.js уже установлен на компьютере, на котором создан проект. `npm install` не нужен.

Для остановки сервера — `Ctrl+C` в его терминале. Если порт занят, задайте другой `PORT` в `.env` и перезапустите сервер. Изменения `.env` требуют перезапуска.

## Что работает

- Реальная история профессиональных матчей BO3: даты, команды, турниры, результаты серий, карты и итоговый счёт раундов. Отдельных раундовых событий в этой загрузке нет.
- Исторические участники матчей: K/D/A, ADR, KAST, рейтинг BO3 и дополнительные доступные показатели.
- Поиск матчей по команде, турниру и загруженным игрокам; просмотр подробностей.
- Рейтинг команд, статистика игроков, история участника.
- Личные встречи команд и игроков. Для игроков отдельно считаются встречи **по разные стороны** и игры **в одной команде**. Это результаты команд, а не матрица личных убийств.
- Прогноз победы профессиональной команды: Glicko-2 и логистическая регрессия поверх рейтингов, формы, опыта, паузы и личных встреч.
- Последовательная проверка на поздней части истории: log loss, Brier score, accuracy, ROC-AUC, калибровка, сравнение шести моделей и базы 50/50 на одной выборке.
- Бесплатные коннекторы FACEIT и PandaScore, требующие ваших бесплатных API-ключей.
- CSV матчей, карт и показателей игроков по матчам для дальнейшего анализа.
- SQLite, кэш исходных JSON-ответов, журнал загрузок, ограничение скорости, повторы при 429/5xx, сохранение уже загруженного при ошибке.

В `data/cs2.sqlite` уже загружена **реальная** выборка BO3: около 44 000 матчей с 27.09.2023, дня выхода CS2. Поддельные матчи в рабочую базу не добавляются. Точные текущие объёмы и фактический период показываются на главной. Лимит импорта означает, что фактический период может быть короче запрошенного.

## Бесплатные источники

### BO3 — работает сразу

В разделе «Источники и импорт» выберите BO3, период, лимит матчей и лимит подробной статистики. Начните с 500 матчей и 100 подробных записей.

- Используется публичный **неофициальный**, не требующий ключа JSON-интерфейс `https://api.bo3.gg/api/v1`.
- Это не обещание бессрочного доступа, полноты, лицензии на перепродажу или стабильной схемы. Для публичного коммерческого продукта условия источника нужно отдельно согласовать.
- Список матчей и статистика игроков загружаются отдельно. Если подробных данных нет, в таблицах стоит `—`, а не выдуманный ноль.
- Повторный импорт обновляет матчи без дубликатов и дополняет следующие записи без статистики. Недоступная статистика повторно проверяется через сутки; успешная не запрашивается повторно.
- Матчи идут от новых к старым. Для более ранней истории уменьшите конечную дату или увеличьте лимит. Максимум за один запуск — 10 000 матчей и 2 000 запросов статистики матчей.
- Пауза между запросами — не менее 800 мс. При 401/403 приложение останавливается, не пытаясь обходить ограничения.
- Серии с технической победой `defwin` исключаются. Запрашивается CS2 и проверяется дата не ранее 27.09.2023; у неофициального источника нет гарантии правильной маркировки переходного периода CS:GO → CS2. Для первой проверки лучше брать 2024 год и новее.
- Сохраняется состав **из статистики матча**, не сегодняшняя команда из профиля игрока.

Пример через терминал:

```powershell
npm run sync -- --source bo3 --from 2026-06-01 --to 2026-09-19 --limit 1500 --statsLimit 150
```

Не запускайте одновременно несколько CLI-импортов. Веб-интерфейс допускает только одну загрузку за раз. Если сервер перезапущен посреди загрузки, уже сохранённые записи останутся; повторите импорт. Журнал отличает завершённые запуски от незавершённых.

### FACEIT — бесплатный ключ

1. Откройте [FACEIT Developer Portal](https://developers.faceit.com), войдите в свой аккаунт.
2. Создайте приложение в App Studio и **Server side API key**. [Инструкция FACEIT](https://docs.faceit.com/getting-started/authentication/api-keys/).
3. Добавьте ключ в локальный `.env`:

```dotenv
FACEIT_API_KEY=ваш_ключ
```

4. Перезапустите сервер, выберите FACEIT в импорте и укажите ники через запятую.
5. После загрузки переключите верхнюю «Выборку» на FACEIT.

```powershell
npm run sync -- --source faceit --nicknames "Ник1,Ник2" --from 2026-08-01 --to 2026-09-19 --limit 200 --statsLimit 200
```

История ищется по указанным игрокам, а не по всем пользователям FACEIT. Перекрывающиеся матчи дедуплицируются. Период передаётся явно, чтобы API не ограничил ответ месяцем по умолчанию. Длинные переполненные окна истории делятся по времени. Для каждого матча сохраняются все доступные участники и статистика в пределах лимита. В BO3/профессиональные команды эти записи автоматически не смешиваются.

FACEIT-команда в этой базе — точная пятёрка, а не постоянная организация. Экспериментальная проверка FACEIT считает собственный Elo игроков и среднее по пятёрке; сегодняшний официальный FACEIT Elo не подставляется в прошлое. Матчи без пяти известных игроков на каждой стороне исключаются из проверки. KAST и рейтинг не выдумываются, если endpoint их не отдаёт.

**Живое подключение FACEIT не проверялось без пользовательского ключа.** Адаптер, сборщик истории и обработка статистики проверены на тестовых ответах по документированной схеме.

### PandaScore — бесплатные результаты

Создайте бесплатный аккаунт на [PandaScore](https://app.pandascore.co), добавьте `PANDASCORE_API_KEY` в `.env`, перезапустите сервер. Используется только бесплатный `/csgo/matches/past`, без платных endpoints статистики. Подробные данные игроков и карт из платного тарифа не запрашиваются.

```powershell
npm run sync -- --source pandascore --from 2026-08-01 --to 2026-09-19 --limit 1000
```

Живой импорт требует вашего ключа и пока проверен только тестами. [Официальное распределение endpoints по тарифам](https://developers.pandascore.co/docs/plan-reference). У PandaScore отдельные условия для betting-related использования; обычный бесплатный тариф не следует считать разрешением на такой продукт.

## Модель

Это **исследовательская модель**, а не готовая прибыльная стратегия.

Рабочий прогноз — логистическая регрессия по семи признакам, посчитанным строго до начала матча. Главный из них — логит Glicko-2, остальные добавляют форму, опыт, паузу и личные встречи. Все движки (наивная доля побед, Elo, Elo + margin of victory, Glicko-2, регрессия, регрессия со стекингом рейтингов) считаются на одной и той же истории одним проходом и сравниваются на отложенных 20%.

Результат после аудита 20.09.2026: 44 016 матчей BO3, 35 203 строки обучения и 8 808 тестовых встреч с 20.02.2026. Матчи у самой границы исключены из fit, поскольку их исход ещё не был доступен. Текущие значения воспроизводятся командой `npm run research -- audit`.

| Модель | Log loss ↓ | Brier ↓ | Accuracy ↑ | ROC-AUC ↑ |
| --- | --- | --- | --- | --- |
| Доля побед (наивная база) | 0.6698 | 0.2384 | 59.60% | 0.6306 |
| Elo K=40 | 0.6341 | 0.2218 | 63.63% | 0.6847 |
| Elo + margin of victory | 0.6355 | 0.2221 | 63.83% | 0.6867 |
| Glicko-2 | 0.6252 | 0.2177 | 64.81% | 0.7002 |
| **Логистическая регрессия** | 0.6168 | 0.2142 | 65.76% | 0.7106 |
| Регрессия + рейтинги | 0.6167 | 0.2142 | 65.87% | 0.7107 |
| Всегда 50/50 | 0.6931 | 0.2500 | 50.00% | 0.5000 |

Это ретроспективная оценка на данной выборке, не подтверждение преимущества над рынком и не «потолок» качества. При продолжении исследования нужен новый будущий тест, зафиксированный до подбора player-признаков.

- Признаки: разница Elo, логит Glicko-2, разница доли побед, разница формы за 10 матчей, личные встречи, разница опыта, разница паузы. Свободный член равен нулю, обучение идёт на зеркальных строках, поэтому `p(A,B) + p(B,A) = 1` тождественно.
- Glicko-2: старт 1500 ± 350, τ = 0.5, один матч = один рейтинговый период, RD растёт во время простоя. Параметры — текущая конфигурация; вывод об оптимальности требует воспроизводимого эксперимента.
- Веса регрессии подбираются только на разогреве. Текущий код не запускает автоматический подбор гиперпараметров или абляцию; прежние исследовательские утверждения без сохранённого протокола не считаются независимой проверкой.
- Единица обучения — встреча/серия, не отдельная карта. Победа обновляет рейтинг после окончания матча.
- Сторона состава — список id: одна команда для профессиональных матчей и пять игроков для состава FACEIT, поэтому в матчмейкинге рейтинг принадлежит игрокам, а не названию.
- Статистика карт пока не входит в прогноз. Исторические map win rates можно добавлять при расчёте только по завершённому прошлому. Veto допустимо лишь для прогноза после его публикации.
- Первые приблизительно 80% хронологической истории — разогрев; последние 20% — последовательная оценка. Совпадающие времена начала не разделяются на границе. Параметры фиксированы и на тесте не подбираются.
- Матч, ещё не закончившийся к моменту другого, не влияет на его прогноз. Если корректного времени окончания нет, результат откладывается на 24 часа от начала.
- Прогноз 50/50 даёт 0.5 в accuracy независимо от случайного порядка сторон. В log loss и Brier используются сами вероятности.
- Команды с менее чем пятью предшествующими матчами выделены как холодный старт. Дополнительно показываются метрики без них.
- Исторические составы используются в FACEIT-модели как известные до старта. Профессиональная модель пока не учитывает составы, veto карт, формат серии, силу лиги, патчи и статистику игроков.
- Сильные показатели внутри слабой региональной выборки не означают высокий глобальный рейтинг. Результат чувствителен к охвату и давности истории.
- Рейтинг BO3 — собственный показатель BO3, не HLTV rating. Средние ADR/KAST на экране игроков — средние по доступным матчам, не взвешенные глобально по раундам. Внутри серии FACEIT ADR взвешивается по числу раундов, если они известны.
- Идентификаторы имеют префикс источника. Автоматического сопоставления BO3 ↔ FACEIT ↔ PandaScore нет, чтобы не склеить разных людей и не посчитать один матч дважды.

Следующие исследовательские шаги, в порядке ожидаемой отдачи:

1. **Рейтинг по игрокам для профессиональных матчей.** Это проверяемая гипотеза: рейтинг игроков может переносить информацию при переходах между организациями. Нужны достаточная предыстория составов, обработка замен и независимая проверка на одинаковой выборке.
2. **Сила лиги / тир турнира** как признак: 2 322 команды в выборке живут в очень разных по силе регионах.
3. **Зафиксировать будущий тестовый период** и проверить модель на матчах, которых не было в базе на момент фиксации весов. Протокол и гиперпараметры нужно зафиксировать заранее.
4. Сравнение с закрытием линии на одинаковых матчах проверяет качество относительно рынка; нужны timestamped котировки и оценка неопределённости. Accuracy сама по себе преимущества не доказывает.

Текущая статистика целевого матча может быть целевой переменной или материалом анализа, но не входным признаком его собственного прогноза.

## Player-level исследование

Новые данные учтены: **5 444** матча со статистикой, **2 970** игроков, **55 134** строки игрок × матч; полные пятёрки с обеих сторон есть в **5 213** матчах. Подробное покрытие — **12,37%** всей истории и смещено к свежим месяцам; добор более ранней статистики идёт помесячно. Из кэша восстановлены размены, клатчи и доступные суммы экономики без повторных сетевых запросов.

- **«Скаутинг»**: срез по времени, окно/минимум матчей, прозрачный индекс формы, n_eff, сравнение с рейтингом BO3, поиск и CSV. По умолчанию 90 дней и минимум 10 матчей. Это описательная эвристика, не RAPM и не новый предиктор победы.
- **«Готовность данных»**: охват по месяцам, полнота составов, пропуски полей и этапы исследования.
- Исторические роли задаются с подтверждением в `data/roles.json`. Файл пока отсутствует: роли неизвестны, используется общая когорта.
- Подготовлен SQLite feature store и атомарный импорт нормализованных раундов. Реальных раундов пока **0**, автоматический парсер .dem не реализован.

### Вклад игроков (RAPM)

Раздел «Вклад игроков» и эндпоинт `/api/rapm`. Вероятность исхода собирается из подписанных ±1 коэффициентов десяти игроков с L2-штрафом, а не из рейтинга названия команды. λ выбирается на валидации 60–80%, тест — последние 20% матчей; метки, не завершившиеся к границе, исключаются с обеих сторон; интервал разницы Brier считается bootstrap-ом по матчам.

Замер на 5 213 матчах с полными составами, тест 1 043 матча с 20.08.2026, λ = 5 (эти же числа лежат в опубликованном снимке):

| Модель | Log loss ↓ | Brier ↓ | Accuracy ↑ | ROC-AUC ↑ |
| --- | ---: | ---: | ---: | ---: |
| RAPM по игрокам | 0.6441 | 0.2263 | 63.0% | 0.671 |
| Glicko-2 на тех же матчах | **0.6286** | **0.2195** | **64.8%** | **0.694** |

ΔBrier = **+0.0068** в пользу командной базы, 95% интервал **[−0.0003; +0.0141]** едва задевает ноль: с ростом данных RAPM не догоняет базу, а отстаёт сильнее. **Знание пятёрки пока не улучшает предматчевую вероятность.** Две измеримые причины показаны прямо в интерфейсе: 302 из 1 043 тестовых наблюдений содержат игрока без коэффициента, а 1 397 игроков полностью неотличимы от партнёров — они встречаются ровно в одних и тех же наблюдениях, и регуляризация делит общий сигнал поровну. Для неизвестного игрока прогноз не считается: подставлять средний коэффициент нельзя.

Раундовый режим (Mirage, CT/T и стартовая экономика) реализован в том же модуле, но остаётся в статусе `insufficient_data` — импортированных раундов 0.

`npm run research -- audit` сохраняет полный отчёт в `data/reports/bo3-research.json`; `npm run research -- enrich` повторно восстанавливает недостающие поля из кэша с предварительным backup. Форматы ролей, раундов и API: [RESEARCH_FORMATS.md](RESEARCH_FORMATS.md). Проектный pipeline актуализирован в [документе проекта](CS2_Player_Rating_—_Pipeline_и_метрики_проекта.md).

## Рынок и карты

Раздел «Рынок и карты» и эндпоинт `/api/market-lab`. Два отдельных вопроса.

### Помогает ли история команды на конкретной карте

Да, и это первый player/map-признак, который проходит проверку. Единица — отдельная карта, прогноз условен на то, что карта уже известна. Базовая модель видит только Elo и сглаженный винрейт команды по картам; вторая добавляет Elo, винрейт и опыт команды именно на этой карте. Обе обучены на одних и тех же строках, внутри серии каждая карта видит состояние до старта серии.

| Модель карты, тест 11 458 карт с 21.03.2026 | Log loss ↓ | Brier ↓ | Accuracy ↑ | ROC-AUC ↑ |
| --- | ---: | ---: | ---: | ---: |
| Без признаков карты | 0.6580 | 0.2330 | 60.41% | 0.639 |
| С историей на карте | **0.6524** | **0.2305** | **61.12%** | **0.650** |

ΔBrier = **−0.0025**, 95% интервал по недельным блокам **[−0.0039; −0.0011]** — весь ниже нуля. Прирост есть на 7 из 8 основных карт, сильнее всего на Overpass, Inferno и Nuke. Основной вес остаётся у общего Elo, а среди признаков карты самый тяжёлый — **сколько раз команда уже играла эту карту**, а не её винрейт на ней: команды чаще играют свои карты, потому что сами их пикают. Это косвенное подтверждение идеи «пик не своей карты», но не бэктест ставок: timestamps veto и котировок на отдельные карты в базе нет.

### Можно ли оценивать вероятность точнее рынка

Инструменты готовы, данных пока нет. Главное правило, которое они проверяют: **точнее рынка ≠ выгодно**. При вероятности 65% и коэффициенте 1.50 EV = 0.65 × 0.5 − 0.35 = **−2.5%** ещё до комиссии; безубыточность при 1.50 — 66.67%. Калькулятор в разделе показывает то же на любых числах: при 65% и 1.50 / 2.70 модель на 0.71 п.п. выше рынка без маржи, но маржа 3.7% съедает всё.

- Котировка выбирается только из доступных **до** момента решения; последняя цена перед стартом хранится отдельно и используется только для CLV. Снятая котировка не возвращает старую цену.
- Банк 2 000 ₽ резервирует ставку до расчёта матча: одновременные ставки не могут потратить ещё не полученный выигрыш.
- 6 правил отбора (фаворит модели, EV > 0 / 2 / 5 / 7.5 / 10%) × 5 размеров ставки (flat 100 ₽, 1% / 2% банка, ¼ / ½ Kelly с лимитом 5%). Комиссия с выигрыша и расход от суммы ставки задаются отдельно.
- ROI и разница Brier с рынком — с интервалами по недельным блокам. 30 сочетаний на одной выборке — это множественное сравнение: лучшее из них само по себе ничего не доказывает. Честный сигнал — устойчиво положительный CLV.

Бесплатный источник — [OddsPapi](https://oddspapi.io/us/docs/get-historical-odds): история с января 2026, 250 запросов в месяц, CS2 — `sportId=17`. Один запрос истории = один матч, то есть около 240 матчей в месяц. Этого хватит проверить сопоставление и получить первые CLV, но не для значимого ROI.

```powershell
# ODDSPAPI_API_KEY=ваш_ключ в .env
npm run odds -- sync 2026-09-01 2026-09-08 5 pinnacle
npm run odds -- report 0 0
```

`sync` берёт окно до 10 дней и не больше `limit` матчей за прогон, делает backup базы и сопоставляет события по названиям и времени; неоднозначные пары отбрасываются, а не угадываются. `report [комиссия] [расход]` пишет CSV со сравнением, сделками, кривой банка и калибровкой в `data/reports/`. Ключ передаётся только в запросе и не попадает ни в кэш, ни в тексты ошибок. Можно загрузить и свой архив: `npm run odds -- import file.json`, формат — в [RESEARCH_FORMATS.md](RESEARCH_FORMATS.md).

Статья из обсуждения — [Dagaev, Stoyan. Parimutuel betting on the eSports duels: Evidence of the reverse favourite-longshot bias, 2020](https://www.sciencedirect.com/science/article/abs/pii/S0167487020300660) — изучает пари-мутуэльный рынок CS:GO, где выплата зависит от итогового пула. К фиксированным коэффициентам современных букмекеров её выводы напрямую не переносятся.

## Файлы и данные

```text
src/adapters.js     Нормализация BO3 / FACEIT / PandaScore
src/collectors.js   Пагинация, периоды, сбор статистики
src/http.js         Кэш, паузы, retries, сохранение 64-bit Steam ID
src/db.js           SQLite: matches, cache, runs, round_features
src/model.js        Elo, Glicko-2, логистическая регрессия, walk-forward
src/rapm.js         Вклад игроков: L2-регрессия, временной split, bootstrap
src/lineups.js      Контракт составов, общий для Node и браузера
src/export-site.js  Снимок модели в docs/ для GitHub Pages
docs/               Статическая витрина: index.html, data.json, rapm.js
src/analytics.js    Backtest, H2H, прогноз, показатели команд и игроков
src/server.js       Локальный HTTP API и статический интерфейс
src/research.js     Скаутинг, роли, аудит качества
src/features.js     Нормализованные раунды, backup, восстановление кэша
src/research-cli.js Аудит, enrichment, импорт раундов
src/cli.js          Загрузка из терминала
public/            Интерфейс без внешних библиотек и CDN
test/              Изолированные тесты с базой в памяти
data/cs2.sqlite     Рабочая база и исходные ответы API
.env               Ваши ключи, исключён из git
```

Исходные JSON-ответы остаются в таблице `cache`: URL запроса, время получения, ответ. В URL не записываются API-ключи. 64-битные числовые Steam ID сохраняются строками без потери точности. Нормализованные записи — JSON в таблице `matches`, ключ `(source:externalId)`. Структура позволяет добавить новый коннектор без изменения интерфейса.

Для копирования базы остановите приложение и CLI-импорты, затем скопируйте папку `data` целиком, включая `-wal` / `-shm`, если они остались. Не публикуйте `.env` и исходные данные как лицензированный продукт без проверки условий источников.

Локальные GET endpoints: `/api/summary`, `/api/matches?q=...&page=1`, `/api/match?id=...`, `/api/teams`, `/api/players`, `/api/h2h?type=players&a=...&b=...`, `/api/predict?a=...&b=...`, `/api/backtest`, `/api/research`, `/api/scouting`, `/api/export?type=matches|players|maps|scouting`. Везде можно добавить `source=bo3|faceit|pandascore`. Импорт доступен через интерфейс и CLI.

Сервер слушает только `127.0.0.1`; ключи не передаются браузеру. Изменения выполняются только с токеном локальной страницы; `.env` и база не раздаются как статические файлы. CSV защищён от интерпретации строк как формул. Это локальный инструмент, не конфигурация для публичного сервера.

## Проверки

```powershell
npm test
npm run check
```

Обновить статическую витрину после новой загрузки данных:

```powershell
npm run site
```

Скрипт пересобирает `docs/data.json` из локальной базы и на выходе сверяет вероятность, посчитанную по экспортированным весам, с вероятностью самой модели: при расхождении сборка падает. Страница не ходит в сеть и не содержит ключей.

Тесты проверяют отсутствие утечки будущих исходов (и в рейтингах, и в признаках), перекрывающиеся матчи, границу временной выборки, свойства Glicko-2, зеркальность регрессии, пропущенную статистику, точность Steam ID, исторический состав, повторный импорт, источник идентичности, пагинацию, FACEIT H2H, rate limit/cache, CSV и локальный HTTP API. Тестовые данные никогда не попадают в рабочую базу.
